# 飞书文档巡检表报告设计

## 目标

把巡检报告产物从独立飞书电子表格改为原生飞书文档。文档正文使用原生表格承载实际运行数据：部门合并表头、巡检图片行、对应结果行，以及现有 Token 用量信息。原始参考表只用于确定视觉结构，不复制其业务数据。

## 方案选择

采用“原生 Docx 表格 + 表格单元格内原生图片块”。相比在文档中嵌入电子表格，它能让报告本身保持为文档；相比把整张表渲染成一张大图，文字仍可复制、搜索，图片也可单独查看。

飞书文档表格由 XML 写入，`colspan` 表达部门合并表头。创建表格后回读带 block ID 的 XML，按“巡检图片”行取得每个图片单元格的 block ID，再在对应单元格内创建并上传图片块。

## 文档结构

每 12 张图片形成一个三行表格分段：

1. 第一行：左侧为“巡检项”，其余列按连续部门分组合并。
2. 第二行：左侧为“巡检图片”，其余列分别放入实际运行图片。
3. 第三行：左侧为“巡检结果”，其余列写入与上方图片一一对应的结果；不合格、无法判断和执行失败同时写入说明。

全部图片分段之后保留 Token 用量区块。文档标题继续使用“任务名 + 巡检报告 + 时间”。

## 组件边界

- `report_document.py`：纯函数渲染文档 XML，并从回读 XML 中解析图片单元格 ID；不访问网络或数据库。
- `feishu_client.py`：定义创建文档、追加 XML、回读 XML、在指定父 block 创建图片块、上传图片的协议。
- `lark_cli.py`：以用户身份调用飞书 OpenAPI 和 `lark-cli docs`；连接状态只要求 Docx 创建、读写及图片上传权限。
- `reports.py`：负责持久化导出进度、并发上传和失败重试，不负责拼接 XML 细节。

## 数据流与恢复

导出先创建并保存文档引用，再仅一次写入表格 XML。随后回读文档并保存每张图片对应的单元格 block ID。图片块使用稳定 operation key 创建；上传成功后记录完成状态。重试复用同一文档、同一单元格和同一图片块，只处理未完成图片，不重新执行 VLM 推理。

图片上传并发上限保持为 4。若表格回读数量与本次图片数量不一致，导出失败并保留当前进度，等待显式重试。

## 界面与兼容性

设置页继续只显示当前飞书连接和目标目录，不恢复手填 App ID、密钥或目录 token。任务页和历史页统一称为“飞书文档”。已有电子表格报告链接仍可打开；新建版本从本次改动起产出 Docx。

## 验收

- 新报告 URL 为 `/docx/`，且位于配置目录。
- 12 张样例图片均位于“巡检图片”行，结果位于下一行并一一对应。
- 部门分组为安保 2、工程人员 1、客房 3、前厅 6。
- 样例结果为 10 个合格、2 个不合格，两个不合格说明完整。
- 重试不新建文档、不重复已完成图片；图片上传并发不超过 4。
- 生成报告前后推理尝试次数不变。
- 后端、前端测试、静态检查、类型检查和生产构建通过。
